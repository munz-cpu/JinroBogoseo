# 보스전 연구 운영 가이드

## 프로젝트와 참가 흐름

Unity 6000.6.3f1, URP 17.6, Cinemachine 6.6, Input System 1.20, uGUI 2.6을 사용합니다. 연구 플레이는 아래 세 씬으로 진행됩니다.

| 씬 | 역할 |
| --- | --- |
| `Assets/Scenes/BossStudyStart.unity` | 기존 타이틀 씬. 열면 인트로 메뉴로 이동 |
| `Assets/Scenes/BossStudyIntro.unity` | 메인 메뉴, 플레이테스트 안내·동의, 참가자 등록 |
| `Assets/Scenes/BossStudyGame.unity` | 게임 진행, 보스전과 재도전, 난이도 조절 및 도전 기록 |
| `Assets/Scenes/BossStudyReview.unity` | 별점, 사후 안내와 데이터 제외 |

기본 빌드는 인트로의 메인 메뉴에서 열립니다. 네 씬은 하나의 참가자 세션과 전송 대기열을 공유합니다. 진행 중인 참가자는 **이어하기**로 저장 상태에 맞는 화면으로 돌아갑니다. **설정**에서 전체 음량을 바꿀 수 있고, **통계**에는 도전·사망 횟수와 마지막 도전 기록이 표시됩니다. **실험 약관**에서는 동의 문구와 보관 기간, 문의처를 볼 수 있습니다. 원본 `Assets/Scenes/BossFight.unity`는 Unity Editor에서 일반 전투용으로 열 수 있습니다. 게임 진행 씬은 원본의 전투 코드와 에셋을 사용하며 1페이즈 9개 공격과 별도 낙석, 2페이즈 12개 공격을 총 22개 ID로 추적합니다.

연구 UI는 각 씬의 **연구 참가 화면** 아래에 배치되어 있습니다. 하위 페이지는 Play Mode에서 현재 단계에 맞춰 켜집니다. 씬의 **연구 세션**은 첫 진입에서만 활성화되고 이후 씬 전환에서도 유지됩니다.

참여에 동의하면 서버 배정 직후 전투를 시작합니다. 메뉴에서 **이어하기**를 눌러도 바로 전투로 들어갑니다. 승리하면 전투 화면이 멈추고 그 위에 별점 패널이 뜹니다. 성취감 별점 1~5점을 선택하거나 건너뛰면 사후 안내로 이동합니다. 게임 화면에서 **ESC**를 누르면 일시정지 메뉴에서 음량과 사망 횟수를 확인할 수 있습니다. **메뉴로 돌아가기**를 선택하면 진행 중인 도전은 중단으로 기록되며, 타이틀에서 같은 참가자로 새 도전을 시작할 수 있습니다. 일시정지 시간은 플레이 타임에서 제외합니다. 실제 목표 횟수와 그룹은 플레이 화면에서 숨깁니다. 사후 안내에는 참가자 UUID, 문의처, 제외 요청 버튼이 있습니다.

사후 안내의 **다시 하기**를 누르면 이전 세션을 미전송 기록과 함께 로컬의 `completed-studies` 폴더에 보관하고 새 동의 화면을 엽니다. 미전송 기록은 이전 참가자 ID로 백그라운드에서 전송하며, 게임을 재실행한 뒤에도 이어서 처리합니다. 동의 후 새 세션 ID를 발급해 서버에서 그룹을 다시 추첨합니다. 패배하면 **Enter**를 눌러 현재 세션과 배정을 유지한 채 다음 도전을 시작합니다. 이전 세션을 제외하려면 당시 참가자 ID를 사후 안내에 표시된 담당자에게 전달합니다.

**동의하고 시작**은 서버에서 배정받은 뒤 전투를 엽니다. 서버를 사용할 수 없으면 동의 화면에서 **동의하고 오프라인 시작**을 선택합니다. 오프라인 등록은 UUID로부터 A=3회, B=7회, C=12회, D=12회(고정 어려움)를 각각 25% 확률로 배정합니다. 이 배정은 `offline-v1`으로 기록되며 온라인의 `RESEARCH_GROUPS` 설정과 독립적입니다. 전송에는 `POST /participants/offline`을 지원하는 서버가 필요합니다. 배포 빌드에 유효한 HTTPS 주소가 아직 없으면 게임은 실행되고, 주소가 설정된 버전으로 업데이트할 때까지 기록을 로컬에 보관합니다.

동의 직후 UUID와 임의의 256비트 참가자 토큰을 저장합니다. 서버 응답이 유실돼도 같은 UUID와 토큰으로 재등록하며 배정은 SQLite에서 유지합니다. 배정 후에는 재실행하거나 오프라인 상태에서도 재도전·설문을 진행할 수 있습니다. 도전 시작, 도전 종료, 설문 제출, 전송 확인을 `Application.persistentDataPath/boss-study-v1.json`에 원자적으로 교체 저장합니다. 등록 확인 후 도전과 설문을 저장 순서대로 재전송합니다. 연결 오류·408·429·5xx와 오프라인 등록 경로의 404는 최대 60초 간격으로 재시도합니다. 현재 참가자의 그 밖의 4xx는 자동 재시도를 멈춥니다. 도전과 별점의 전송 상태는 플레이 및 후기 화면에서 숨깁니다. 데이터 제외 요청은 미전송 도전·설문을 지우고 우선 처리합니다. 최초 등록 응답을 받기 전에 제외를 누르면 같은 자격 증명으로 등록 상태를 확인한 뒤 제외합니다.

진행 중 정상 종료 시에는 해당 시점까지 기록하고, 강제 종료 시에는 마지막 5초 주기의 체크포인트를 사용해 다음 실행에서 `interrupted`로 제출합니다. 실제 도전 번호에는 두 종류의 중단도 포함합니다. 기록에는 하드웨어 ID, Windows 계정명, MAC 주소를 넣지 않습니다. 로컬 파일에는 참가자용 비밀 토큰이 들어 있으므로 참가자별 Windows 프로필 또는 전용 테스트 환경을 사용하세요.

## Unity Inspector 설정

1. Project 창에서 `Assets/Settings/BossStudySettings.asset`을 선택합니다. 이 에셋은 네 씬의 **Study Scene → Study Scene Entry → 연구 설정**에 연결되어 있습니다. `BossStudyIntro`를 열고 Play한 뒤 **게임 시작**을 누르면 연구 안내가 표시됩니다.
2. **Protocol**에 승인된 동의 안내, 보관 기간(**Retention**), 담당자 연락처(**Contact**), 사후 안내를 입력합니다. 설정을 완료하면 동의 버튼이 활성화됩니다. 저장된 동의는 자동으로 새 문구로 교체하지 않습니다.
3. **Api Url**을 설정합니다. Editor와 Development Build의 로컬 테스트는 기본값 `http://127.0.0.1:8000`을 사용합니다. 참가자 배포 빌드에는 HTTPS API 주소를 입력합니다. Player Settings의 HTTP 설정은 **Development Only**이며, 연구 클라이언트는 개발 환경에서도 루프백 주소의 평문 HTTP만 허용합니다. [Unity PlayerSettings HTTP 설정](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/PlayerSettings-insecureHttpOption.html)
4. **Minimum Level**과 **Maximum Level**로 난이도 곡선의 범위를 조정합니다. **Boss Health**와 패턴의 **Selection Weight**는 X가 낮은 난이도 값, Y가 높은 난이도 값입니다. **Pattern Overrides**의 **Pattern Id**에는 `StudyRecords.cs`의 식별자(예: `fist_sweep`)를 입력합니다.
5. 동의 문구나 보관 조건 변경 시 **Consent Version**, 전투 설정·설문 변경 시 **Settings Version**, 서버 그룹·비율 변경 시 **RESEARCH_ASSIGNMENT_VERSION**을 갱신합니다. 참가자 등록 시 클라이언트 설정 사본을 로컬에 저장하므로 활성 연구 중 기존 참가자의 API 주소와 실험 조건은 해당 사본을 따릅니다. 버전별로 승인된 문구, Inspector 설정과 서버 그룹 설정을 보관합니다.

기존 플레이어 이동·회피·공격과 보스 페이즈 전환을 재사용합니다. 연구 모드에서는 Enter 자동 재시작과 Editor 무적 메뉴를 비활성화합니다. Unity Editor에서 연구 전투 중 페이즈 건너뛰기를 사용할 수 있으며, 2페이즈를 건너뛴 도전도 클리어로 기록·전송합니다. 한 참가자 흐름은 하나의 로컬 파일에 대응합니다. 신규 참가자가 같은 PC를 쓸 때는 다른 프로필을 사용하고, 테스트 파일은 미전송 기록이 없음을 확인한 테스트 환경에서만 정리합니다.

참가자용 빌드에는 기본 Scene List를 사용합니다. 빌드 프로필이 자체 씬 목록을 사용한다면 `BossStudyIntro`를 첫 번째에 놓고 `BossStudyGame`과 `BossStudyReview`를 포함합니다.

## DDA 계산

기본 범위가 0–1일 때 A·B·C그룹은 난이도 0.90에서 시작합니다. 목표 2회 전부터 목표 3회 후까지 S자 곡선으로 0.12까지 내려가며, 이후 0.12를 유지합니다. 예를 들어 C그룹은 10회차까지 0.90, 목표인 12회차에 약 0.63, 15회차부터 0.12입니다.

- 패턴별 취약도는 최근 패배 최대 4회의 `clamp01(Σ(평균 피해 × 피격 횟수) / max(1, 총 실행 횟수 × 25))`입니다. 난이도가 낮을수록 취약한 패턴의 등장 가중치 보간 위치를 최대 0.35만큼 낮춥니다. 직전 전경 패턴을 제외한 가중 무작위 추첨을 사용하고, 1페이즈 배경 낙석의 가중치는 반복 주기에 반영합니다.
- 도전 시작에 보스 최대 HP를 0.94–1.12배로 설정합니다. 공격 속도, 주 공격 간격, 판정 크기, 피해량은 기본 배수 1을 사용합니다.
- 난이도가 높을수록 1페이즈 배경 낙석의 반복 대기가 짧아집니다. 2페이즈에서는 잽·어퍼컷·후려치기 예고에 보조 낙석 한 개가 겹칠 수 있습니다. 착지 지점을 미리 표시하며, 난이도 0–1에서 해당 공격에 겹칠 확률은 5–55%입니다. 보조 낙석의 실행과 피해는 `rock_rain`으로 집계합니다.
- 2페이즈 체력이 30% 미만이면 주먹 두 개가 추가됩니다. 진행 중인 공격이 끝나면 네 손 교차 내려찍기와 네 손 협공을 번갈아 사용합니다. 새 공격의 실행과 피해는 `fist_cross_slam`과 `fist_pincer_combo`로 집계합니다.

목표는 실제 횟수와 목표의 오차를 줄이는 것입니다. D그룹은 첫 도전부터 설정된 최고 난이도를 사용하고, 이후 도전에서도 같은 전투 설정과 패턴 가중치를 적용합니다. D그룹의 목표 12회는 C그룹과 비교하기 위한 기록값입니다. 모든 그룹에서 목표 전 승리를 허용합니다.

## FastAPI 실행과 배포

Python 3.12 환경에서 `ResearchServer` 폴더를 작업 디렉터리로 사용합니다.

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
Copy-Item .env.example .env
.\.venv\Scripts\python.exe -m uvicorn main:app --host 127.0.0.1 --port 8000 --env-file .env
Invoke-RestMethod http://127.0.0.1:8000/health
```

`RESEARCH_GROUPS`는 그룹 ID, 목표 횟수, 가중치의 JSON 배열입니다. 기본값은 A=3회, B=7회, C=12회, D=12회(고정 어려움)이며 각 25%로 배정됩니다. 새 세션에서 같은 그룹을 다시 뽑을 수 있습니다. 기존 참가자의 배정은 환경 변수가 바뀌어도 유지됩니다.

서버에는 영속 볼륨의 SQLite 절대 경로를 사용합니다. Uvicorn 인스턴스와 워커는 각각 하나로 운영하고, HTTPS 역방향 프록시 뒤에서 실행합니다. 프록시에서 요청 본문 크기(예: 256 KiB)와 요청 빈도를 제한하고 Authorization 헤더와 본문을 로그에 저장하지 않습니다. `RESEARCH_ADMIN_TOKEN`을 비워 두면 관리자 API는 비활성화됩니다. 값을 설정한 경우 `GET /admin/sync`에 별도 Bearer 토큰을 전달하면 원본과 시트의 동기화 리비전을 확인할 수 있습니다. 관리자 접근은 운영 네트워크로 제한합니다.

운영자는 고지한 보관 기간이 끝나면 SQLite 원본과 분석 시트, 백업 및 내보낸 사본을 정책에 맞춰 정리해야 합니다. 자동 만료 작업은 포함하지 않았습니다. 참가자가 UI에서 제외를 요청하면 서버는 참가·도전·설문 행을 한 트랜잭션에서 제거하고, 재전송에 의한 재등록을 막기 위해 UUID·토큰 해시·요청 시각만 제외 영수증에 보관합니다. 연결이 복구되면 분석 시트에서 해당 행이 사라집니다. 로컬 파일을 분실했을 때는 사후 안내의 연락처로 UUID를 전달하여 담당자가 별도로 처리할 수 있도록 안내합니다.

## Google Sheets 미러

1. Google Cloud에서 Sheets API를 켜고 서비스 계정을 준비합니다. 새 전용 스프레드시트를 만들고 서비스 계정 이메일에 편집 권한을 줍니다. [Google Workspace 서비스 계정 설정](https://developers.google.com/workspace/guides/create-credentials#service-account)
2. `RESEARCH_SPREADSHEET_ID`에 해당 스프레드시트 ID를 넣습니다. 필요한 경우 `GOOGLE_APPLICATION_CREDENTIALS`에 저장소 바깥의 자격 증명 파일 절대 경로를 넣습니다. 호스팅 환경의 ADC를 사용할 수도 있습니다. ID를 비워 두면 SQLite 저장만 수행합니다. [Google Cloud ADC 설정](https://docs.cloud.google.com/docs/authentication/application-default-credentials)
3. 서버가 `Participants`, `Attempts`, `PatternStats`, `Surveys` 탭을 만들고 지정된 열에 일관된 SQLite 스냅샷을 씁니다. 이 탭의 데이터 영역은 수정하지 말고 분석용 수식은 별도 탭에 작성합니다. 요청이 일부 실패해도 SQLite 저장은 완료되며, Sheets 리비전을 기록하지 않아 다음 주기에 재시도합니다. 행을 추가하는 대신 네 탭의 데이터를 한 원자적 배치로 교체해 중복과 제외된 행을 정리합니다. [Google Sheets 원자적 배치 동작](https://developers.google.com/workspace/sheets/api/guides/batch)

## 데이터 사전

`Participants`에는 참가자별로 마지막 시도의 진행도, 클리어 후 제출한 별점, 실제·목표 시도 횟수, 모든 시도의 플레이 타임 합계(초)와 피해 합계, 마지막 시도의 종료 사유가 표시됩니다. 페이즈 진행률은 해당 페이즈에서 감소한 보스 HP 비율입니다. 이전 버전에서 수집한 미클리어 시도의 페이즈가 확인되지 않으면 진행도를 비워 둡니다.

| API | JSON 및 SQLite 저장 |
| --- | --- |
| `POST /participants` | UUID, 명시적 동의, UTC 동의 시각, 동의·실험 버전. 기존 서버 형식의 연령대·게임 빈도는 새 참가자에서 `undisclosed`로 전송. 응답은 그룹, 목표 도전 횟수, 배정 버전. SQLite에는 토큰의 SHA-256 해시 저장. |
| `POST /participants/offline` | 같은 참가자 정보와 토큰으로 등록하며, 서버가 UUID에서 `offline-v1` 배정을 재현합니다. 기존 온라인 배정을 덮어쓰지 않습니다. |
| `POST /attempts` | UUID, 도전 UUID, 1부터 시작하는 연속 도전 번호, 그룹·목표·버전, UTC 시작·종료, 경과 초, 양측 실제 체력 손실 합계, 두 페이즈의 남은 HP 비율, 종료 시 페이즈와 페이즈 진행률(0~100), 패턴 실행·피격·평균 피해, 난이도 스냅샷·적용 시각·이유, 승리 및 종료 사유(`cleared`, `defeat`, `stopped`, `interrupted`). |
| `POST /surveys` | UUID, 설정 버전, UTC 제출 시각, 승리 여부·실제 횟수, 응답 생략 여부, 성취감 별점 한 개. 생략 시 점수 배열은 비어 있음. 기존 여섯 점수 형식도 수신하며, 새 별점은 시트의 `achievement_score`에 기록함. |
| `POST /withdraw` | UUID와 참가자 Bearer 토큰으로 데이터 제외. 성공 204, 같은 요청 반복 가능. |
| `GET /health` | SQLite 접근 가능 시 `{"status":"ok"}`. 참가자 기록은 공개 API로 읽을 수 없음. |

피해량은 과잉 피해를 빼고 실제로 감소한 HP를 합산합니다. 회복 후 다시 입은 피해도 포함합니다. 패턴 평균 피해는 해당 패턴의 받은 피해를 실제 피격 횟수로 나눈 값입니다. 피해가 없으면 0입니다. 패턴 실행 횟수는 스케줄된 시도 횟수이므로, 전투 종료 등으로 중단된 시도를 포함할 수 있습니다. 경과 초는 도전 시작부터 종료 또는 마지막 체크포인트까지의 실시간입니다.

## 검증 방법과 결과

- 세 씬을 연결한 뒤 Unity Editor 컴파일과 실제 로컬 FastAPI를 사용한 Play Mode 테스트를 통과했습니다. 동의·등록 후 게임 진행 씬으로 이동했고, 클리어 후 후기 씬에서 같은 참가자 세션으로 설문과 데이터 제외를 완료했습니다.
- 서버 테스트는 `ResearchServer`에서 `python -m unittest -v`를 실행합니다. FastAPI 통합 테스트 8개가 통과했습니다. 동의·토큰·가중 배정·재시작 시 동일 배정, 중복 제출, 페이즈 진행률과 참가자별 합계, 클리어 별점과 생략, 제외, 모의 Sheets 오류 및 재동기화를 검증했습니다.
- Unity의 **Tools → Boss Arena → Research → Run Study Smoke Test**는 별도 저장 폴더에 테스트 참가자를 생성합니다. 실제 참가 기록이 없는 Editor에서 `BossStudyIntro`를 열고, 별도 SQLite DB의 서버를 18741 포트로 시작합니다. `RESEARCH_GROUPS`를 `[{"group":"B","target_attempts":7,"weight":1}]`로 설정합니다. 테스트는 메인 메뉴와 이어하기, 씬 전환, 세션 유지, 동의 전 차단, UUID 재로드, 페이즈 전환과 1회 클리어, 연결 실패 후 재전송, 설문 및 제외를 확인합니다. 결과는 `Temp/BossStudySmoke.txt`에 기록됩니다. 피해 입력은 재현성을 위해 실제 전투 체력 메서드에 테스트가 직접 전달합니다.
- **Tools → Boss Arena → Research → Validate DDA and Simulate**에서 DDA 방향·변화폭 4개 검증이 통과했습니다. 실력 3단계, 목표 3종에 각 300명씩 시드 315로 모의 실험합니다. `Temp/BossStudySimulation.txt`에 기록된 조합별 MAE는 1.35–9.97회, ±1회 달성률은 0–63.4%, 중도 종료 및 24회 미클리어 비율은 0–31.7%였습니다. 게임 실측 대신 난이도·실력·학습·확률로 결과를 생성하는 모형이며, 참가자 데이터에서의 달성률은 아직 확인하지 않았습니다.
- 실측 집계는 `python metrics.py study.sqlite3`으로 출력합니다. MAE와 ±1회 달성률 분모는 클리어 참가자, 중도 포기율 분모는 종료가 관측된 참가자(클리어 또는 자발적 종료)입니다. 활동이 재개되지 않은 열린 참가자는 따로 표시합니다.
- `achievement_by_target_attempts`와 `achievement_by_actual_attempts`에는 목표·실제 도전 횟수별 평균 성취감 별점이 각각 표시됩니다. 같은 목표 횟수라도 실험군과 배정·설정 버전이 다르면 각각 집계합니다. `cleared`는 클리어 참가자 수이고 `rated`는 성취감 별점에 응답한 참가자 수입니다. 별점 생략, 미응답, 이전 6문항 응답은 별점 평균에서 제외하며, 별점 응답이 없는 집계의 평균은 `null`입니다.
- 실제 Google 서비스 계정과 스프레드시트가 제공되면 운영 배포 전에 테스트 참가자 하나를 등록하고, Sheets에 반영된 뒤 제외 요청이 네 탭에서 사라지는지 확인합니다. 이번 검증은 모의 Sheets REST 응답을 사용했습니다.
